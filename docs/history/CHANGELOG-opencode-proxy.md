## 2026-10-15（兼容代理：直通路径剥掉「无 encrypted_content 的 reasoning item」的 id）

- **现象（用户截图）**：同一线程继续对话时报 `{"model":"muse-spark-1.3-contributor-free","error":{"code":null,"message":"Referenced reasoning item `rs_1792051783_2` was not found or has expired.","param":null,"type":"invalid_request_error"}}`。
- **根因（实测闭环）**：`rs_1792051783_2` 正是代理**翻译路径** `gen_id("rs")` 合成的思维链 item id（形状 `rs_<unix秒>_<hex序号>`，只有 `summary`、没有 `encrypted_content`）；codex 把它存进线程历史，之后同一线程切到 Responses 原生模型走直通时原样回放，而上游 `/responses` 对这类 item **按 id 查**，查不到即拒。逐项实测（同一份 `user → reasoning → assistant → user` 历史，均带门禁工具）：带 `encrypted_content` 的 reasoning item（无论 id 是否存在）→ 200；**只有 summary + 未知 id → 400**（与截图逐字一致）；只有 summary、无 id → 200；`message` / `custom_tool_call` 带合成 id → 200；`function_call` 只校验「每个调用必须有对应 output」（codex 本来就会带）。
- **改动（`src-tauri/src/codex/compat_proxy/mod.rs`）**：新增纯函数 `sanitize_responses_reasoning_items(&mut Value) -> usize` —— 遍历 `input[]`，对 `type == "reasoning"` 且 `encrypted_content` 缺失/空串/null/全空白 的 item **只删 `id` 字段**（`summary` 与其余字段逐字保留），返回被剥条数；在 `handle_responses_passthrough` 里紧跟 `normalize_responses_tools` 之后、**门禁补丁之前**调用（与「OpenCode 客户端身份」开关无关：协议兼容而非伪装），条数 > 0 时记 `compat_proxy.reasoning_ids_stripped count=N`（info）。没有该类 item 的请求体一个字节都不改（既有「逐字透传」性质保持）。
- **未覆盖**：不做「失败再剥并重试」的兜底（用户选择无条件剥，零额外往返）；不剥其它 item 的合成 id（实测无害）；翻译路径不受影响（历史 reasoning item 在那里被转成 chat 的 `reasoning_content`，id 从不下发）。
- **测试**：单测 3 例（只剥无加密的 id 且 summary 逐字保留 / 无 reasoning item 的请求体逐字不变 / 空串-`null`-缺失-全空白四种形态与带加密内容的保留）；集成 2 例（合成 id 历史经直通路径 → 上游收到的 item 无 id 且 summary 仍在、日志含 `reasoning_ids_stripped count=1`；带 `encrypted_content` 的历史 → id 保留且不记日志）。回归 `cargo test --lib`、`cargo check --all-targets`（零警告）、`npm run format:check`。
- **文档**：README 兼容代理「Responses 直通路径」小节新增「直通路径的历史净化（思维链 item）」条目（含实测判据与为什么只剥 id）。

## 2026-10-15（兼容代理：Responses 直通支持 codex 的 custom 工具 —— apply_patch 双向转换 + 畸形保护）

- **现象（用户截图）**：用 `muse-spark-1.3-contributor-free` 在会话里发「你好」报 `{"model":"muse-spark-1.3-contributor-free","error":{"message":"\`custom\` tools are not supported on this endpoint","param":"tools","type":"invalid_request_error"}}`。
- **定位**：日志显示协议自动判定已生效（`compat_proxy.protocol … protocol=chat` → `protocol_switched … to=responses` → `passthrough status=400`），报错来自直通请求体里的 `tools[].type="custom"`。
- **为什么只能代理侧修（实测）**：① 上游 `/responses` 拒收 `custom` 工具（复现 400），但接受 `function` 工具与历史里的 `custom_tool_call` / `custom_tool_call_output`（均 200）；② codex 的模型目录字段 `apply_patch_tool_type` **只有 `freeform` 一个合法取值** —— 用临时 `CODEX_HOME` 跑 `codex debug models` 实测报 ``unknown variant `function`, expected `freeform` ``，所以 codex 必然把 apply_patch 声明成 custom，改目录/声明侧无解；③ 改成同名 function（单 `input` 参数 + 补丁语法说明）后上游 200，但 codex 对「声明为 custom、却收到 `function_call`」会 `Fatal error: tool apply_patch invoked with incompatible payload`（仓库既有真机结论）→ 响应流必须回译。
- **改动（`src-tauri/src/codex/compat_proxy/mod.rs`）**：① 新增 `normalize_responses_tools(&mut Value) -> Vec<String>`，在**直通路径无条件**把 `custom` 工具改写成同名 function（`custom_tool_description` + `custom_tool_parameters` + `strict:false`，丢弃 `format` grammar；同名以客户端 function 为准、重复只转第一个、无名丢弃），返回被转换的名字集合，并记 `compat_proxy.responses_custom_tools count=… names=…`；② 新增 `ResponsesToolRewrite` / `PendingCall` 与纯函数 `rewrite_responses_frame`：按 SSE 帧改写，把该名字的 `function_call` 调用在**收敛时**整组下发为 `custom_tool_call`（`output_item.added` 改写、一次性 `response.custom_tool_call_input.delta`（解码后的完整文本）+ `.done`、`output_item.done` 改写），并在 `response.completed/incomplete/failed` 的 `response.output[]` 同步改写；其余帧逐字透传；③ 新增 `sse_frame_end` / `parse_sse_frame` 与流式包装 `rewrite_responses_stream`（`stream::unfold` + 装箱 inner stream），新增 `forward_passthrough_rewriting`（2xx 走改写流，非 2xx 原样透传供协议判定）；④ **畸形保护**：被转换调用若最终 `input` 为空 → 记录 `malformed_ids`、抑制该调用的所有帧，收尾改发 `response.failed`（形状与翻译路径一致，`error.code=malformed_tool_call_arguments`）并记 `compat_proxy.malformed_tool_call`；⑤ 没有 custom 工具的请求仍走原 `forward_passthrough`，逐字透传不受影响。
- **测试**：单测 5 例（`normalize_responses_tools` 的转换/顺序/同名去重/无名丢弃/无 tools 不动、帧改写器的 added→delta→done→completed 全链路、非 custom 与非法帧逐字透传、空参数转 `response.failed`）；集成 3 例 + 一个「Responses 原生 + 工具调用」mock（请求侧断言 custom→function 且带补丁语法、无 grammar；响应侧断言 `custom_tool_call` + 解码后的补丁原文且无 `function_call`/`arguments`；无 custom 工具时响应与上游字节逐字一致；空参数时客户端收到 `response.failed` 且日志有 `malformed_tool_call`）。回归 `cargo test --lib` 795 例全绿、`cargo fmt` + `npm run format:check` 通过（前端无改动）。
- **文档**：README 兼容代理条目新增「直通路径的 custom 工具双向转换（apply_patch）」小节（含为什么只能代理侧修、请求/响应两侧行为、畸形保护、历史无需改写）。
- **未覆盖**：不做 patch 自动修复；不处理其它潜在非 function 工具类型（当前 codex 目录下 `shell_type=shell_command`、`supports_search_tool=false`、`experimental_supported_tools` 为空，实测只有 apply_patch 是 custom）。

## 2026-10-15（兼容代理：自动识别模型协议 —— Responses 原生模型直通，不加开关）

- **需求（用户）**：opencode/Zen 里有些模型只支持 `v1/responses` 协议（代理现在一律翻译成 chat，这类模型直接不可用）；要求**不要加翻译开关**，由代理**自动判定**。
- **现象与根因**：`muse-spark-1.3-contributor-free` 等 Responses 原生模型经代理发往 `chat/completions`，被上游以 `400 ModelProtocolUnsupported`（`Model does not support this protocol.`）拒绝；`docs/变更记录.md` 上一版修复只解决了免费层门禁与端点，未处理协议选择。
- **实测（经本机系统代理出口 `localhost:8080`；本机 `http_proxy`/WinINET 均指向它，代理进程的 reqwest 默认会走它，而 node `fetch` 默认不走 —— 这也是先前直连误报 `403 RegionError` 的原因）**：① `/inference/v1/responses` 实测可用（zen.json 原文回放 200、极简 body + 6 个合格工具 200、Streaming SSE 正常）；② **Responses 端门禁与 chat 同源**：`stream` 必须 `true`、`tools` 里至少 5 个「名字 ∈ bash/edit/glob/grep/read/write 且 `parameters.properties` 非空」的声明（5 个 ✅ / 1 个 ❌ / 6 个杂名 ❌ / 空 schema ❌），其余字段（系统提示、历史、`store`/`include`/`prompt_cache_key`/`reasoning`/`text`）都不参与；③ **门禁先于协议检查**：工具不够先 403、够了才暴露 `400 ModelProtocolUnsupported`（两个方向都是这条错误）；④ codex 的 `namespace` 工具上游原样接受（用真实 schema 的 6 个工具 + namespace 工具 → 200）。
- **方案（按用户选择：完全自动、纯学习、直通时翻译专属能力让位）**：`ProxyState` 增 `protocols: Arc<Mutex<HashMap<String, ModelProtocol>>>`（按 model id 记忆、粘滞到代理实例结束）；`handle_any` 的 Responses 入口改为 `handle_responses_auto`（读体+解析 → 按协议分派）；默认 `Chat`，命中协议标记（`ModelProtocolUnsupported` / `does not support this protocol`，大小写不敏感）即改判另一条协议**只重发一次**（重发不再二次切换，避免来回抖），其它 4xx 不改判不写记忆；把原翻译入口拆为 `handle_translated_responses`（行为不变，返回 `ProtocolOutcome`）与新增的 `handle_responses_passthrough`。

- **新增日志**：`compat_proxy.protocol protocol=chat|responses reason=default|learned`（每请求）、`compat_proxy.protocol_switched to=… changed=… detail=…`（warn，学到新协议时）、`compat_proxy.zen_tools` 扩展到直通路径。

## 2026-09-15（Zen 代理：补齐 apply_patch 语法说明 + 补丁失败纠错回灌）

- **现象**：用 Zen 代理跑 `mimo-v2.5-flash` / `mimo-v2.5-free` 做功能修改时，模型在"改文件"这一步团团转——反复调用 `apply_patch` 又反复失败，最后改用 PowerShell 字符串替换绕过。实测 09-14 那条 mimo 会话（rollout + session 日志）：16 次 `apply_patch`、5 次 `apply_patch verification failed: Failed to find context 'version_too_old field @@' in …\app_server.rs`，同回合 203 次 `exec_command`，模型的 reasoning 原话是「The apply_patch tool needs exact context lines… let me try the correct format」→「Let me use PowerShell's string replacement instead, which worked earlier」。
- **根因**：codex 0.154 的 `apply_patch` 声明是 `{"type":"custom","description":"The `apply_patch` tool can be used to edit files. This is a FREEFORM tool, so do not wrap the patch in JSON.","format":{"type":"grammar","syntax":"lark","definition":"start: begin_patch hunk+ end_patch … change_context: (\"@@\" | \"@@ \" /(.+)/) LF …"}}`——**补丁语法只存在于 `format.definition`（lark grammar）里**，description 只有那两句。代理既不下发 grammar（Chat Completions 没有语法约束能力，单测还断言 `format` 不下发），又因为那句 FREEFORM 把 description 整段替换成「编辑文件（apply_patch 语法）。」+「请把完整补丁文本放进 JSON 的 input 字段。」——上游模型因此**拿不到任何补丁格式信息**，只能自创 `@@ 中文描述 @@` 形态的 hunk 头；而 codex 的解析器把 `@@` 之后的整段当作"要查找的文件行"，必然 `Failed to find context`。
- **修复①语法说明**：`custom_tool_description` 新增 `patch_syntax_spec()`——从 grammar 提炼的**纯英文**规范，追加在 `apply_patch` 的函数描述末尾（其它自由格式工具不加）：骨架 `*** Begin Patch` → `*** Update File: <path>` → `@@ <可选：文件里逐字存在的一行>` → 上下文/`-`/`+` 行 → `*** End Patch`；文件块 `*** Update File` / `*** Add File`（后续行以 `+` 开头）/ `*** Delete File` / `*** Move to` / `*** End of File`；硬约束「hunk 头只能是 `@@` 或文件里逐字存在的一行，禁止 `@@ 描述 @@`」「上下文行必须与文件逐字一致、含缩进，先读文件再写补丁」。基底与函数调用约定同时改为英文（`Edit files (apply_patch patch language).` + `This channel is a function call: put the full patch text in the JSON "input" field.`），`input` 参数说明也补上骨架。
- **修复②失败纠错回灌**：`responses_to_chat` 先算出本段历史里失败的自定义工具调用（新增纯函数 `patch_failure_call_ids`：`call_id` 必须来自 `custom_tool_call`，且对应 `custom_tool_call_output` 命中 `apply_patch verification failed` / `Failed to find context` / `Invalid patch` / `Invalid Context`——只认自定义工具调用，避免把恰好打印了同样字样的普通命令输出算进来），命中时在该 `role:"tool"` 消息末尾追加英文纠错提示（`patch_failure_hint`：点明 `@@` 后被当作文件行查找、只能写 `@@` 或原文锚点行、上下文行需逐字复制、并给最小正确示例）。提示只出现在**发往上游**的请求体里，codex 自己的记录与 rollout 不变；历史每次重建，不会累积膨胀。
- **修复③诊断量化**：`request_log_fields` 新增 `patch_failures=<n>`（`patch_failure_count`，0 表示历史干净），`StreamState` 增加 `patch_failures` 并在 `proxy_stream_response` 里填充，收尾写进 `zen_proxy.stream_summary` 与 trace 摘要，`SuspiciousFacts` / `suspicious_flags` 新增标记 `patch_retry`（`patch_failures > 0` 命中）。
- **测试**：新增 5 例（描述含语法骨架与禁止项、非 apply_patch 的自由格式工具不加语法段、失败补丁的工具结果被追加提示而其它输出逐字不变、`patch_failure_count` 只计自定义补丁失败、收尾摘要含 `patch_failures` 与 `patch_retry`），并按新增字段更新 `custom_tool_is_exposed_as_single_input_function`、`request_log_records_reasoning_effort`、`suspicious_flags_cover_each_branch` 的断言；`cargo test --lib` 633 例通过，`cargo clippy --lib` 无新增告警（文件既有的 `needless_borrow` 等告警未动）。

## 2026-09-12（Zen 代理：翻译路由按 base_url 路径、透传零路径转换、参数即时生效、日志重建）

- **根因**：代理只注册了 `.route("/v1/responses", …)`，而现实提供方常没有 `/v1`（DeepSeek 官方 base_url 就是 `https://api.deepseek.com`），codex 请求的是 `/responses`，于是落进 `fallback` 静默透传——既不翻译、也没有任何 `zen_proxy.*` 日志，多轮排查"没日志"的困惑由此而来。本机实测（codex-cli 0.149.0 + 本地探针服务器）：`base_url=http://127.0.0.1:X/zen/v2` → 请求 `POST /zen/v2/responses`，写成 `…/zen/v2/`（带尾斜杠）同样如此，`…/X/` → `POST /responses`（不会出现 `//responses`）；codex-ui 生成模型目录时请求 `{provider base_url 路径}/models`。两条规则都据此确定。

- **透传零路径转换**：`passthrough_url` 只用 base_url 的 scheme/host/port，入站 path 与 query 原样发出（不再剥离 `/v1`、不再拼接 base_url 的路径）。使用约定随之明确：**本地 provider 的 base_url 路径必须与「模型提供方的 base_url」一致，只把 host 换成本机代理**。
- **可观测性**：透传补 `zen_proxy.passthrough method=… path=… status=…`（2xx info、其余 warn）；客户端把 `/responses` 打到非期望路径时记 warn `zen_proxy.path_unmatched path=… expected=…`，直接给出"本地 base_url 该填什么"。
- **参数即时生效**：`ZenProxyHandle` 增加生效中的 base_url（归一化值），`apply()` 的重启条件从"端口变化"改为"端口**或**上游地址变化"；`https://a/` 与 `https://a` 这类等价写法不触发重启，真实换地址保存即生效、无需重启 codex-ui。同端口重建时监听可能尚未释放，`start()` 增加最多 20×50ms 的绑定重试。
- **日志文件重建**：`session_log::write_at` 写入前检查当天文件是否仍存在，被外部删除时重新 `open_file`（此前句柄留在 `inner.current`，删除后当天不再产生新日志，正好误导"看有没有新日志文件"的验证）。
- **设置页**：「转发目标地址」改名为「**模型提供方的 base_url**」；说明段落里的本机 base_url 改为按当前上游地址的路径动态生成（`http://127.0.0.1:{端口}{上游路径}`，默认 `/zen/v1`），并写明"只换 host"的约定。
- **测试**：`passthrough_url_*` 四个用例改到新语义；新增归一化/路由派生单测、`handle_any` 分派（`/zen/v2/responses` 走翻译且上游收到 `/zen/v2/chat/completions`、无路径上游的 `/responses` 走翻译、`/responses` 打到 `/zen/v1` 上游时透传并记 `path_unmatched`、非 POST 同路径透传）、>2MB 请求体不再 413、`apply` 重启语义（同端口同上游复用、换上游立即重启且旧上游不再收到请求、端口变化重启、关闭即停止，用上游记录的 `x-opencode-session` 判定是否重启）；前端新增"标签文案"与"本机 base_url 提示跟随上游路径"两条断言。回归 `cargo test --lib -- --test-threads=1` 582 用例通过、`cargo build` 通过、`vitest` 与 `vue-tsc` 通过。

## 2026-09-11（Zen 代理：`x-opencode-session` 优先取请求头 `session-id`）

- **取值来源**：转发给 Zen 的 `x-opencode-session` 改为优先使用入站请求头 **`session-id`**（codex 的 OpenAI 协议会话标识——`codex-api::build_session_headers` 行次模型请求都会带 `session-id` 与 `thread-id`），并统一补 **`ses_` 前缀**（值本身已以 `ses_` 开头则原样使用）：UUID `3f1a2b3c` → `ses_3f1a2b3c`。缺失、`to_str()` 失败（非可见 ASCII）或 trim 后为空时，回落到代理生命周期内稳定的 `ses_*`（`ProxyState.session`，启动时 `random_id("ses")` 生成）。
- **落地位置**：`zen_proxy.rs` 新增 `opencode_session(headers, fallback)`；`forwarded_request_headers(headers, fallback_session)`（`/v1/*` 透传路径）与 `forward(..., fallback_session)`（`POST /v1/responses` → Chat Completions 翻译路径）都改为经该函数取 session，参数由 `session` 更名为 `fallback_session` 并更新注释；两个调用点仍传 `&state.session`。
- **保持不变**：`x-opencode-client: desktop`、`x-opencode-project: global` 固定、`x-opencode-request: msg_*` 行请求随机；入站 `session-id` / `thread-id` 头仍随其它头一起转发给上游；URL 映射、UA 与 Authorization 透传行为不变，无新增状态或缓存。
- **测试**：新增单测 `opencode_session_prefers_client_header`（UUID → 加前缀、`ses_abc` → 不重复加、前后空白 → trim 后加前缀、缺失/纯空白/非可见 ASCII 字节 → 回落 `ses_fixed123`）；新增集成测试 `forwards_chat_prefers_client_session_header`（翻译路径上游收到 `ses_3f1a2b3c`，仍带固定 client/project 头与 `msg_*`）与 `passthrough_prefers_client_session_header`（透传路径 `GET /v1/models` 收到 `ses_client-session-42`）；既有不带 `session-id` 的三个用例继续断言 `ses_fixed123`（回落未变）。`cargo test --lib zen_proxy` 22 例通过、`cargo check --all-targets` 0 警告。
